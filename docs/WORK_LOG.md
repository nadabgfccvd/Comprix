**Janela 5 (15:12 UTC) — análise de causa raiz da corrida + COORDENAÇÃO com agente paralelo.**
- Cron disparou DOIS turnos simultâneos sobre o mesmo repo; o outro turno já estava a meio
  caminho do mesmo conserto quando este começou a investigar. Para não atropelar: este turno
  só ANALISOU (instrumentação FLAKE-DEBUG temporária nos helpers, já removida) e não editou
  os testes do outro. Conclusões complementares abaixo — somam-se ao conserto do outro turno.
- **Mecanismo confirmado empiricamente (red run instrumentado):** `estado` dos VMs é `combine`
  de correntes Room independentes; após uma escrita existem estados INTERMEDIÁRIOs (um campo
  novo, outro velho). `espera` de campo único retorna no intermediário; o assert seguinte lê o
  campo velho → vermelho só sob carga. Caso pego em flagrante: Historico `o periodo afina o
  resumo` — `espera{compras.size==2}` voltou com `resumo.quantidadeCompras==0` (assert 1≠0).
- **Conserto correto (que o outro turno já aplicou parcialmente):** (a) `setMain` no EVENT LOOP
  do runBlocking (single-thread, FIFO) em vez de `Unconfined` — mata as retomadas inline em
  threads do executor do Room; (b) condições de espera COBRINDO TODOS os campos que o assert
  seguinte lê (feito em Historico; ainda faltam os sites abaixo).
- **Hazard restante nº 1 — condição não-total (crash em vez de retry):** Lojas
  `esperaLojas { it.single().estabelecimento.nome == "..." }` — `.single{}` em lista AINDA VAZIA
  lança `NoSuchElementException` (foi a falha vista na suíte vermelha). Conserto de 1 linha:
  usar `any { ... }`. Vale em QUALQUER dispatcher.
- **Hazards restantes (espera campo único → assert campo diferente; dobrar o campo no espera):**
  - Catalogo: `espera{grupos.isNotEmpty()}` → assert `produtosLocais.isEmpty()`; `espera{total==0}`
    → asserts `grupos.isEmpty() && produtosLocais.isEmpty()`; `espera{!buscaLimitada}` → assert
    `total==120`.
  - Categorias: `espera{totalDeProdutos==2}` → assert `produtosPorCategoria[hortifruti]==2`;
